# 共通規格の設計メモ

新しい行事の導線資料を作るときの方針。
現状の2本はまだ個別実装だが、**どこが共通化でき、どこができないか**は確定している。
次に手を入れるときはここから読むこと。

---

## 1. 3層に分ける

全部を1つの規格に押し込むと壊れる。性質の違うものが混ざっているため。

| 層 | 内容 | 共通化の可否 |
|---|---|---|
| **1 操作UI** | 方眼背景／左サイドバー／再生・停止・早送り・巻き戻し／時間バー／速度／場面切替 | **完全に共通**。現状2本でほぼ同一コード |
| **2 場** | トラック・体育館・音楽室・廊下の下地と座標系 | **プリセット化できる** |
| **3 中身** | 下記の2型に分かれる | 型による |

### 3層目の2つの型

**導線型**（入場・退場・移動）
経路＋隊列＋時間だけで書ける。状態を持たない。時刻 t の純関数。
→ **設定ファイルだけで1本作れる**。ここが効率化の本丸。
→ 時間バーを自由にドラッグできるのもこの性質のおかげ。

**模擬型**（リレー）
チームの速度差、順位、バトンパス、待機列の増減といった状態を持つ。
時刻 t の関数では書けず、逐次計算が要る。巻き戻しはスナップショットで実現している。
→ 層1・層2だけ流用し、中身は個別に書く。無理にデータ化しない。

**判定の目安**：「誰が何番目に着くか」が結果に影響するなら模擬型。
決めた通りに動くだけなら導線型。

### 導線型の中の2つの書き方

導線型は「時刻 t の純関数」という性質を守れば、書き方は1つでなくてよい。
`gas/undokai/nyutai.html` には2つ同居している。

| 書き方 | 使いどころ | 実装 |
|---|---|---|
| **経路追従** | 1回の連続した移動。隊列が形を保ったまま進む | `makeGroup()`。経路＋隊列＋開始時刻 |
| **キーフレーム** | 何段階かに分かれた移動。同じ人が何度も動く | `advState()`。要素ごとに時刻から位置を引く |

**経路追従は1回の移動しか表せない。** 前つめのように
「出る → つめる → 出る → つめる」と繰り返す場面は、無理に経路に乗せず
キーフレームで書く。どちらも t の純関数なので、時間バーは同じように効く。

判定：**同じ要素が2回以上動くならキーフレーム。**

## 2. 導線型の部品（現状 `gas/undokai/nyutai.html` に実装済み）

切り出すならこの5つ。

### field
場の形と座標系。今はトラックのみ。
- スタジアム形（直線2本＋半円2つ）を半径 r で描く
- 弧長 s から座標を引く `posAt(s, r)`
- 直線上の x から s を引く `sTop(x)` `sBot(x)`

体育館やホールを足すときは、この「1次元の道のり s から座標を引く」という形を守ること。
隊列の追従計算がすべてこれに乗っている。

### path
経路。円弧・直線をつなぎ、角を2次ベジェで丸める。
- **角を丸めるときは、円弧を丸め半径ぶん手前で打ち切ってからつなぐ**
  （打ち切らないと経路が後戻りして隊列がガクガクする。実際に踏んだ）
- 距離で引けるよう累積長を前処理する `prep()` / `at(d)`

### formation
隊列。先頭追従型。
- 各要素は中心からの「前後のずれ a」「左右のずれ b」を持つ
- 位置は `at(中心距離 + a)` を取り、その点の法線方向に b ずらす
- これでカーブでも隊列が崩れない。剛体回転させると角で振り回されるので使わない
- 到着時の並びは、**経路終端の向きから a と b を逆算して決める**。手で書かない
- 経路の前後を隊列の奥行きぶん延長しておかないと、先頭か最後尾が経路からはみ出す

### timeline
時刻 t から全体を描く。状態を持たない。
- 再生・停止・早送り・巻き戻し・任意位置へのシーク
- 総尺は各組の `開始時刻 + 所要時間` の最大値から自動算出

### ui
サイドバーと操作ボタン。層1そのもの。

## 3. 作るときに毎回引っかかる点

- **交錯**：左右対称の配置だと、片側のブロックで必ず動線が交差する。
  同時に動かさず、時間をずらすこと。現状は白組が抜けきってから赤組を出している。
  「抜けきる時間」は `(中心からの距離 + 隊列の奥行き) ÷ 速度` で見積もれる。
- **人数**：長方形1つ＝何人かを決めておく。端数が出ても図では区別しない方が読みやすい。
- **回戦・順番**：先に出る者が隊列の先頭、後に出る者が最後尾。
  並び終わった状態から逆算して入場順を決める。
- **向き**：図の上下左右は校舎・鉄棒などの目印で固定する。
  現場と合っているかを必ず紙で確認してから作ること。180度回転の作り直しは高くつく。

## 4. GASで配信するときの制約

HtmlServiceは `<script src="...">` で外部ファイルを読めない。**必ず1ファイルに結合する**。
方法は2つ。どちらを採るかは校務PCでNodeが使えるかで決まる。

| 方式 | 長所 | 短所 |
|---|---|---|
| ビルド結合（Node） | ローカルでは分割したまま開発できる | Nodeが要る。ビルドを忘れると反映されない |
| GAS側 include | ビルド不要。`<?!= include('core_ui') ?>` で差し込む | ローカルで直接開けない。coreを`.html`として置く必要がある |

**Nodeの可否が不明なうちは、単一ファイルのまま運用するのが安全。**
現状の2本は外部依存ゼロなので、この問題自体が起きていない。
共通化に踏み切るのは、資料が4〜5本たまって重複が実害になってからでよい。

## 5. 現状の未確定事項

`gas/undokai/nyutai.html` は以下を仮定で作っている。実態と違えば直すこと。

- 1ブロック＝4列（赤黄青緑）×3行（回戦）。**「4回戦ある」という情報とは食い違っている**。
  4回戦なら `var HEATS=3;` を `4` にすれば1組8枚（2列×4行）で全体が自動的に組み直される。
  前つめの段数も回戦数から出しているので、ここを変えれば場面ごと組み直る。
- クラス番号は行と列から機械的に割り振っており、実際の編成とは無関係。
- 退場は左上・右下ブロックから、2か所同時。

前つめの場面で新たに置いた仮定は次の3つ。

- **前の向き**：`r=0`（1回戦）のがわを前とし、そちらへ1マスずつ詰める。
  図の回戦ラベルと揃えただけで、実際の校庭でどちらが前かは確認していない。
  逆なら `BC` の `A` `B` の y を入れ替えるか、`blockPos` の `sgn` を反転する。
- **走り終えた児童の場所**：出発ブロック `A`→`C`、`B`→`D` へ移る（`ADV_TO`）。
  `C` `D` は退場の開始隊形として既にあった座標で、走行方向（上の直線は x 減少、
  下は x 増加）とも一致する。**走る経路そのものは描いていない。**
  出発ブロックで消え、走り終わりブロックに現れる。経路を見せたいなら別途作る。
- **到着の並び**：先に走った回戦が前（`r=0`）。退場が1回戦先頭であることと揃えた。
